# Independent novelty audit: findings.jsonl rows 37–55

Audited 2026-09-19 against the checked-out HBase commit `1790942bb2`. This is a **targeted** prior-art review, not proof that an unindexed report does not exist. I checked each ledger claim against its named regression and Surefire result, the cited production branch, relevant existing-test scenarios, the linked ASF Jira descriptions, and selected `apache/hbase` commit/PR history. ASF Jira REST text searches paired the distinctive method with its exception or state term; GitHub issue/PR searches used the same terms. No Maven run or shared ledger edit was made in this audit.

**Count-sensitive conclusions.** Row 40 is the clearest known-root overlap: [HBASE-18415](https://issues.apache.org/jira/browse/HBASE-18415) already states that a timed-out Admin request can be retried with a new nonce after the first request changed state, so the second returns a state exception. The backup-specific orphan-cleanup effect is plausible but was not exercised end to end. Row 54 is already excluded from the independent count and should remain paired with row 53. Rows 38, 43, and 53 reproduce their code paths but need a contract/policy judgment before calling them independently new bugs. The NPEs in rows 37, 47, and 52 follow branch-selected coordination states; absence of a literal `throw` keyword is an evidence distinction, not by itself a reason to reject them.

## Priority for reporting

The stronger currently reproduced and reasonably distinct cases in this range are **39, 41, 42, 44, 46, 48, 49, 50, 51, and 55**. They still carry provisional novelty because exact-match search cannot establish universal absence. Cases **37, 45, 47, and 52** have test-backed state failures but broader historical or transport-boundary caveats. **38** is a documented deprecated-API limitation with a possible false-failure consequence; **43** needs a product contract judgment; **53** follows a longstanding intentional Master fail-stop policy and needs a guarantee that the observed abort is erroneous. **40** should be described as a backup-specific consequence of the known [HBASE-18415](https://issues.apache.org/jira/browse/HBASE-18415) mechanism, and **54** is already correctly excluded as a second manifestation of 53.
