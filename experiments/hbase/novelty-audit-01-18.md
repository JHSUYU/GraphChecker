# Findings 1–18: HBase novelty and evidence audit

Audit date: 2026-09-19. Baseline: local apache/hbase checkout at commit 1790942bb2d46f41f1b4aed94db85e6f5bd18a1a, plus the test additions and run logs named in findings.jsonl. This is a bounded review of these 18 entries, relevant existing tests, and targeted ASF Jira/apache/hbase PRs; absence of a search hit does not establish universal novelty. “Distinct” means no exact predecessor identified and a distinct causal guard or update path is shown. “Related” means prior work addresses a nearby path or the same bug family. “Unverified” means the claimed production sequence is not fully established by the test. The ledger itself was not edited.

Current ledger counts 17 of these 18 toward 50 (#2 is a candidate). I found **no proven exact duplicate** among #1–18, but #4 and #6 are close to existing reported defect families, and #14 lacks an end-to-end durable replay test. A strict count of newly demonstrated production defects should hold these three pending review, yielding **14 provisional entries** from this range. That is a recommendation to re-evaluate, not a ledger mutation. For #4, the branch bug is real under the injected clock value, but natural production reachability remains unmeasured. For #6, the global cache branch is still unfixed, but the clear-then-repopulate race was already reported and fixed for table/namespace permissions. For #14, two serialized procedure objects reaching the same afterReplay semaphore guard does not prove two such records coexist in a real ProcedureStore.

The test uses controlled key injection and time rather than an end-to-end rolling Master/RegionServer cluster; that bounds the finding, but no exact prior report was found.

4. **HBASE-SPLIT-EQUAL-CLOCK-001 — related existing failure family; production reachability unverified. Hold from strict new-production count.** [TestSplitTableRegionProcedure.java](/u/vnr3ne/hbase/hbase-server/src/test/java/org/apache/hadoop/hbase/master/assignment/TestSplitTableRegionProcedure.java:153) manually sets Master time equal to the parent region ID after creating and filling the region. It does not show an ordinary newly created region being split in the same millisecond or a real Master clock rollback to exactly the parent ID. [HBASE-20182](https://issues.apache.org/jira/browse/HBASE-20182) also documents the invariant that the first daughter timestamp exceeds the parent.

## Cross-entry and count implications

- **#12 versus #13:** same API family and test file, but #12 is an injected post-map-flush failure with an unretryable half-commit, whereas #13 succeeds and omits namespace descriptor migration. They are separate roots, not duplicate count entries. Existing rename tests cover normal table mapping and input constraints, not either interleaving.
- **#13 versus #18:** both leave a namespace pointing at a deleted/renamed group and fail the same CreateTableProcedure guard. #13 is a missing update in renameRSGroup; #18 is a race between CreateNamespaceProcedure validation and removeRSGroup's descriptor scan. A fix only for one producer does not repair the other.
- **#7 versus #15:** both use FS peer storage; #7 needs partial removal and reuse of the same ID, while #15 needs concurrent complete removal during a list/read pair. Their failure predicates and fixes differ.
- **#6 versus #10:** both end in AccessDeniedException, but #6 is a live clear/repopulate interval and has [HBASE-28984](https://github.com/apache/hbase/pull/6485/files) as an explicit same-mechanism precedent; #10 is startup continuing after a failed first watch. Count roots separately if #6 is retained as a new affected scope.
- **#17 versus #20/#24:** same final exclusive-marker exception, three separate leak/repair branches as described in #17. They may be grouped under an umbrella backup-session invariant, but are not duplicate call-site bugs.

Recommended immediate ledger review: #6 for known-root novelty, #4 for an already reported split collision family plus artificially forced timing, and #14 for absence of durable replay proof. #2 already remains outside the count. The other 14 counted entries remain **provisionally** distinct on this bounded official-source review; several deliberately use fault or scheduling injection and their stated test scope should be preserved in any public claim.
