# Master control-plane coordination audit (continuation)

Scope: table, namespace, RSGroup, and replication procedure transitions. This file records full test-workload reads and exclusions; it is separate from the counted findings ledger.

## Fully read workloads and traced production paths

### Namespace delete versus table create: excluded by one held lock across normal states

- Read all 231 lines of `hbase-server/src/test/java/org/apache/hadoop/hbase/master/procedure/TestDeleteNamespaceProcedure.java`. It covers successful deletion, absent/reserved/nonempty namespaces, and procedure recovery/rollback with double execution. Its nonempty test creates the table before deletion; it does not submit a table creation while namespace deletion is in PREPARE.
- `DeleteNamespaceProcedure.prepareDelete` counts table descriptors and fails a nonempty namespace (`DeleteNamespaceProcedure.java:198-220`); `deleteDirectory` later explicitly throws `IOException` if a table directory appears (`:235-246`). This initially suggests a prepare-to-delete window.
- `AbstractStateMachineNamespaceProcedure.acquireLock` takes the namespace exclusive lock (`:79-88`), while `AbstractStateMachineTableProcedure.acquireLock` calls `waitTableExclusiveLock` (`:94-103`), which takes the same namespace's shared lock before the table lock (`MasterProcedureScheduler.java:668-684`). `Procedure.holdLock` defaults to `false`, but that does **not** release the lock at every state boundary: `StateMachineProcedure.execute` returns `{this}` for a next state (`StateMachineProcedure.java:188-201`), and `ProcedureExecutor.execProcedure` short-circuits `{this}` into an immediate next iteration in the same held-lock invocation (`ProcedureExecutor.java:1838-1846`), releasing only at its final `:1946`. `DeleteNamespaceProcedure` has no normal yield override or child procedure between PREPARE and DELETE_DIRECTORIES. Thus normal table creation cannot interleave there. No candidate is counted.

### Specific-region reopen versus region state: already represented and expected stale name

- Read all 481 lines of `TestReopenTableRegionsProcedureSpecificRegions.java`. It tests CLOSED known region, invalid names, mixed names, valid subsets, batching, disabled tables, configuration precedence, and serialization. `testReopenKnownClosedRegionWithAnotherRegionOpen` is the existing finding `HBASE-REOPEN-KNOWN-CLOSED-001` and is not a new root.
- `ReopenTableRegionsProcedure.getRegionLocationsForReopen` explicitly throws `UnknownRegionException` for requested names absent from the current OPEN-reopen list (`:337-365`); the tests already check invalid-name and CLOSED-region variants. Split/merge after an external caller captures a region name can also make it stale, but that is the ordinary lifecycle of an identity-scoped request. No distinct invariant requiring automatic remapping of that request was established.

### Flush family versus descriptor modification: excluded by table lock

- Read all 65 lines of `TestFlushTableProcedure.java` and all 99 lines of `TestFlushTableProcedureBase.java`. The fixture starts three RegionServers with a three-family table and nonempty memstores. Tests cover normal flush, disabled/deleted table exceptions, and explicit family-list flushes. They do not overlap a family deletion with a flush.
- `FlushTableProcedure.preflightChecks` explicitly throws `NoSuchColumnFamilyException` if a requested family is absent (`FlushTableProcedure.java:123-130`). Although a concurrent table modification could otherwise change the descriptor, `FlushTableProcedure.acquireLock` takes a table shared lock (`:71-85`), while `ModifyTableProcedure` inherits the exclusive table lock (`AbstractStateMachineTableProcedure.java:93-103`). Both locks also carry a namespace shared lock in `MasterProcedureScheduler.java:668-770`. A submitted modify cannot remove the family while the flush procedure holds its shared lock. No candidate is counted.

### Concurrent modify descriptor check: existing tests cover the guard

- `ModifyTableProcedure.prepareModify` compares the descriptor captured at submission with the one read under its table lock and throws `ConcurrentTableModificationException` when they differ (`ModifyTableProcedure.java:446-457`). `HMaster.modifyTable` captures the old descriptor before submitting the procedure (`HMaster.java:2934-2955`). `TestModifyTableProcedure.java` already has several concurrent-modification cases asserting this exact exception (`:446-604`). RSGroup `setRSGroup` submits `masterServices.modifyTable` procedures (`RSGroupInfoManagerImpl.java:1219-1249`) rather than writing a table descriptor behind the scheduler. This is a known optimistic concurrency guard, not a new cross-component root.

### Replication sync-state upgrade: impossible public precondition

- `ReplicationPeerConfig.isSyncReplication()` is derived from nonblank `remoteWALDir` (`ReplicationPeerConfig.java:129-133`); `ReplicationPeerManager.preUpdatePeerConfig` explicitly forbids changing that directory (`ReplicationPeerManager.java:255-260`). Thus updating an asynchronous peer into a synchronous peer while retaining `SyncReplicationState.NONE` cannot pass public prevalidation. The transition guard at `ReplicationPeerManager.java:273-281` is unreachable under this proposed sequence.

## RSGroup ZooKeeper multi retry after committed delete: verified candidate

- Public `Admin.removeRSGroup` reaches `RSGroupAdminServiceImpl.removeRSGroup` (`:248-263`) and `RSGroupInfoManagerImpl.removeRSGroup` (`:370-399`). The group must be empty and unreferenced; an ordinary newly added empty group meets these guards. `flushConfig` first removes its row in `hbase:rsgroup` and replaces the in-memory holder (`RSGroupInfoManagerImpl.java:614-635,683-689`), then `saveRSGroupMapToZK` emits a `deleteNodeFailSilent` for an old group in `prevRSGroups` (`:693-721`).
- `ZKUtil.toZooKeeperOp` translates this apparently fail-silent deletion into a strict `Op.delete` (`ZKUtil.java:1225-1238`). The caller chooses `multiOrSequential(..., false)`; its `NONODE` switch arm enters `if (runSequentialOnMultiFailure)` with false and falls through to the explicit `throw ke` (`:1283-1300`). `RecoverableZooKeeper.multi` retries the entire transaction after `CONNECTIONLOSS` without checking whether the first attempt committed (`RecoverableZooKeeper.java:666-691`). If its first real multi deletes the znode but its ACK is lost, the retry returns `NONODE`; the RSGroup catch invokes `masterServices.abort` and throws `IOException` (`RSGroupInfoManagerImpl.java:722-727`). This is a cross-component relation between ZooKeeper's committed state and the client's retry state, not an absent-group input error.
- Matching unit workloads: `TestRecoverableZooKeeper` already injects an ACK loss after a real `setData` via replacement of private `RecoverableZooKeeper.zk`, but never tests multi. `TestZKMulti.testSingleFailure` proves `deleteNodeFailSilent` with `runSequentialOnMultiFailure=false` throws `NoNodeException`, but does not put a lost ACK between two multi calls. `TestRSGroupsAdmin1.testNamespaceConstraint` and `TestRSGroupConfig.testSetNonDefaultGroupConfiguration` remove groups successfully; neither injects a ZooKeeper retry. These prior tests were listed `full` in the shared reading index before this continuation; their relevant methods and the complete `TestRecoverableZooKeeper` file were reviewed here.
- Exact-prior search (official Apache Jira, repeated 2026-09-19 with RSGroup/remove/multi/ConnectionLoss/NoNode terms): [HBASE-2611](https://issues.apache.org/jira/browse/HBASE-2611) discusses multi retry in *replication queue migration*, and [HBASE-25583](https://issues.apache.org/jira/browse/HBASE-25583) addresses a RegionServer's legacy replication-log `NONODE` crash. Neither describes RSGroup removal's committed-delete/lost-ACK/retry path; no exact prior surfaced in that search. The source documentation for `RecoverableZooKeeper` acknowledges that a repeated standalone delete can return `NONODE`, but its standalone `delete` handles that case while `multi` does not. This is a search boundary, not proof that no older report exists.
- Verified mini-cluster test: `hbase-server/src/test/java/org/apache/hadoop/hbase/rsgroup/TestRSGroupZKMultiLostAckDelete.java` replaces the Master's `RecoverableZooKeeper.zk` with a ZooKeeper subclass. Its first targeted `multi` calls the real `super.multi` to commit the deletion, then reports `ConnectionLossException` as a lost ACK. RecoverableZooKeeper retries the same transaction; the real ZooKeeper returns `NoNodeException`. Public Admin adds and removes a healthy empty control group, establishing that a valid group can be removed normally. The faulted call invokes the real `RSGroupInfoManagerImpl.removeRSGroup` directly to capture its internal `IOException` before Master abort races the client RPC; it does not assert that a public Admin RPC reliably delivers that exception to its caller. The test asserts exactly two targeted multi calls, the `IOException`'s `NoNodeException` cause, Master abort, and group removal in the manager holder, `hbase:rsgroup` table, and a separate ZooKeeper client's view. The injected connection is restored in `finally`.
- Evidence: `JAVA_HOME=/tmp/hbase-jdk17/usr/lib/jvm/java-17-openjdk-amd64 PATH=/tmp/hbase-jdk17/usr/lib/jvm/java-17-openjdk-amd64/bin:$PATH mvn -pl hbase-server -am -Dtest=TestRSGroupZKMultiLostAckDelete -Dsurefire.failIfNoSpecifiedTests=false -DfailIfNoTests=false test` succeeded (`/tmp/hbase-rsgroup-zk-multi-lost-ack-test.log:1496,1528`; Surefire `hbase-server/target/surefire-reports/org.apache.hadoop.hbase.rsgroup.TestRSGroupZKMultiLostAckDelete.txt`: 1 run, 0 failures/errors, 17.26 s). The Surefire output log records the table mutation completing, a `RecoverableZooKeeper` retry after the injected `ConnectionLossException`, the actual `NoNodeException` stack through `ZooKeeper.multiInternal` → `RecoverableZooKeeper.multi` → `ZKUtil.multiOrSequential` → `RSGroupInfoManagerImpl.saveRSGroupMapToZK`, and the Master `ABORTING` message (`...TestRSGroupZKMultiLostAckDelete-output.txt:839-874`). The test cannot establish the probability of a real lost ACK, but it establishes the outcome when ZooKeeper commits a multi and the client receives a connection loss, which is a reachable distributed-systems state.
- Model: `hbase-server/src/test/resources/adhoc-coordination/rsgroup-zk-multi-lost-ack-delete.smt2`, checked with `/tmp/hbase-z3/usr/bin/z3`, gives `sat/unsat/unsat` for the committed-plus-ACK-lost case and the delivered-ACK / uncommitted-first-multi controls. It explicitly requires the table deletion and holder removal before the ZK retry, a formerly existing znode, and `runSequentialOnMultiFailure=false`.
