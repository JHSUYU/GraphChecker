# Findings 19–36: novelty and evidence audit

Audit date: 2026-09-19. Baseline: `apache/hbase` commit [`1790942bb2d46f41f1b4aed94db85e6f5bd18a1a`](https://github.com/apache/hbase/commit/1790942bb2d46f41f1b4aed94db85e6f5bd18a1a). I read ledger rows 19–36, their stated regression and Surefire reports, the relevant current source branches, nearby existing tests, ASF Jira descriptions using the Jira REST API, and matching `apache/hbase` history. “No exact predecessor found” means this targeted search, not proof of global novelty. New regressions are uncommitted local files; green tests assert the bad branch, while red tests deliberately fail their final desired-health assertion. Report values below are `tests/errors/failures/skips`.

The verdicts separate **prior-art novelty** from **system-level proof**. A related Jira about the same component or exception is not automatically an exact duplicate. Conversely, a unit test that supplies a state by mock or direct table mutation does not prove that the complete public workflow produces that state.

## Cross-row counts and material caveats

- **No exact ASF Jira or `apache/hbase` PR/commit duplicate was identified** in this targeted audit. Rows 22's FS/ZK variants, 20's scanner/early-return variants, 32's possible restore variant, and 36's quota-deletion variant already belong to one finding each.
- **Rows 17, 20 and 24 share a final stuck `ACTIVE_SESSION_YES` state but have independent repair sites:** crash before a RUNNING marker (recovery protocol), delete early exit outside its `finally`, and merge `RuntimeException` cleanup omission. A single exception-safe `finally` at one call site does not repair the other two.
- **Rows 23 and 25 share an ownerless lock protocol but violate ownership in different callers:** an unsuccessful contender cleans up, while repair assumes a live RUNNING session is abandoned. A lock owner token would harden both, yet repair would still need a separate liveness policy. Keep two call-site findings; label them one protocol-risk family in aggregate summaries.
- **Rows 30 and 33 are not duplicates:** map-key miss before completion versus map hit after failure. The public API's documented failed-with-error behavior makes row 33 a strong bug, not merely a confusing status value.
- **Potential count corrections:** row 31 should not be counted as a confirmed correctness bug without a stronger public contract or unrecovered caller failure; row 35 should not be counted as fully end-to-end verified before offset-failure and cleaner/shipper replay are exercised. Rows 21 and 24 retain source-level bug evidence but should be labeled limited-workload proofs. Row 26's locator timeout is proved, while the claimed scanner exception path is manually bridged in the test.

The new regressions were not rerun in this audit. Their on-disk Surefire reports were inspected directly; deliberate-red cases failed at the expected final health assertion according to the ledger's existing evidence. This file does not change `findings.jsonl` or the shared reading indexes.
