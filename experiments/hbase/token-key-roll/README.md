# HBase token key roll: delayed notification

This is a hand-built SMT model of the HBase unit test
[`TestAuthenticationTokenKeyRollCoordination.java`](/u/vnr3ne/hbase/hbase-server/src/test/java/org/apache/hadoop/hbase/security/token/TestAuthenticationTokenKeyRollCoordination.java:64). It uses GraphChecker's path, family arm, state join, and wire handoff semantics. GraphChecker's recorder cannot run this HBase 4.0 workload as-is: HBase targets Java 17, while the recorder uses a customized Java 8 VM. The Java test is the execution check; the SMT file checks that its causal constraints admit the failure and reject the timely-notification control.

Run `z3 -smt2 token-key-roll.smt2`. The two answers must be `sat` and `unsat` (with a value list between them). The `sat` model places issuance at roll + 100 ms and verification at roll + 1001 ms. The leader has removed the old key at roll + 1000 ms, but the token remains valid until roll + 1100 ms. In the `unsat` control, the issuer has received the new key before signing, so the verifier finds it.

The model assumes successful key publication, deletion, and refresh, matching the test's intended path. It abstracts token bytes and cryptographic password verification because the target exception is decided by the key-id lookup before password regeneration. The two `currentKey` arms are chosen by notification ordering; this is a state pairing choice, not a synthetic token value. The token-key equalities represent its handoff from issuer to verifier. The leader's `allKeys` and ZooKeeper contents are separate states, so refresh cannot restore a deleted old key.
