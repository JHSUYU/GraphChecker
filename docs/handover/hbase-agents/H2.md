## (d) Lessons and traps (HBase, non-obvious)

1. **ZK as in Solr works.** RecoverableZooKeeper public ops wrap unchanged private `*Retrying` methods, and the HOOK
   rows (experiments/hbase/doors.jsonl, 7 ZOOKEEPER rows) place the door on the hook call outside the retry loop.
   Decodes: `RecoverableZooKeeper.causynthDecoded(data, product)` in MasterAddressTracker and ZKSecretWatcher.refreshNodes.
   The fault markers do exist as DECLARED_SITE in getData/getChildren/exists. Evidence: HZ15-34 static_scope_map.
   A READ-door fault is still offered only through askFetches, i.e. a provenance cell whose objects a decode
   registered (34 above).
2. **Removing a clock from the seed can unplace another node's clock.** My masterSystemTime workaround (1c1abcc349)
   took master0's only seed clock cells away, so master0's activation clock (T0) got no instant: Composer#placed
   anchored only on same-node seed cells. Its arm still named it, so T0 was a free symbol and every claim "moved
   nothing" (HZ17-mat refuted/0000-0003, FORMULA_SAT movedRoots {}; gap DECLARATION_MISSING "...no instant on the
   recording's timeline"). H5's 208ac1899 places by the nearest same-clock anchor of any node in the session and
   refuses arms on unplaced cells. Trap: any tree workaround that drops a clock read can do this again.
   Check the candidate for clock_domain__ on every clock symbol a fatal names.
3. **Periodic chores fire in slow replays.** A recording under the VM takes about 5 min, a seed replay 15-60 min, so
   5-minute chores fire only in the replay. In HZ17-24 the balancer moved regions at +7.7 min, a close stayed in
   CLOSING and the test's put retried forever. The catalog janitor re-ran, hbck ran at +61 min, and hbase:meta flushed on
   HRegion's hard-coded SYSTEM_CACHE_FLUSH_INTERVAL (5 min, not configurable: a tree change in HRegion.shouldFlush).
   Fixed in f9340f2aab. Find what ran by grepping the replay log for `\.Chore\.[0-9]+\]` and
   "missed its start time"; chores of 10-60 s periods also run in the recording and are harmless.
4. **34 without Kerberos.** Tree c0f65a942c: `RpcServer.CAUSYNTH_TOKEN_SECRETS` ("causynth.hbase.token.secrets") makes
   createSecretManager build the token managers with security off. The workload is TestCausynthTokenKeys (leader
   generateToken, the other server's retrievePassword). Leadership: master0 held keymaster in the HZ15-34 recording (runtime_trace STORE_WRITE /hbase/tokenauth/keymaster).
5. **Heads on lift11 were TERMed.** I had started heads with setsid nohup from my shell on lift11. A stop-run.sh of one
   round covering lift11 also ended the other rounds' ssh clients (exit 255, then the peer watchdogs TERM the payloads,
   20:40:09-18), and a seed replay even ran on lift11. stop-run.sh with LIFTS=lift05-07 does not reach a head on lift11,
   so a "stopped" run went on there. Start heads by ssh on your own hosts, and pass every host where a run can live in
   LIFTS when stopping.
6. **Wait loops can match themselves.** `pgrep -f '<string>'` inside a `zsh -c` whose own command line contains that
   string never ends. Use the `[x]` grep trick or wait on a pid.
7. **NFS lag.** A jar built on lift05 can be invisible on lift11 for minutes (`ls target/` fails while `ssh lift05 ls`
   shows it), and `git worktree add` of the HBase tree takes 5-10 min. Check on the build host.
8. **master-active-time's workload** (TestCausynthMasterActiveTime) must use one master that stops and joins before
   `cluster.startMaster()`. With no WAL, a standby taking over while the old master flushes loses the open procedure.
   The target occurrence is master1's report: `auto0/master1#epoch0/region/REGION.f3a7cc84...#1`.
