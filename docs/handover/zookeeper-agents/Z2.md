1. ZOOKEEPER-5094 (PR 2459): check zk-bugs-trunc-sync
---------------------------------------------------------------------------------------------------------------------
Faulty logic: Learner.java:924. Learner.shutdown runs `zk.shutdown(self.getSyncMode().equals(SyncMode.SNAP))`, so a
sync that fails in TRUNC mode keeps its ZKDatabase. Fix: fork branch fix-trunc-sync-shutdown-state (926ca7da9 +
46c8b43a1) shuts down fully for SNAP or TRUNC.

Mechanism on master:
- In TRUNC mode, `snapshotNeeded` is true, so `writeToTxnLog = !snapshotNeeded` is false (Learner.java:647).
- Until NEWLEADER (:746) arrives, PROPOSAL+COMMIT are applied to memory only, through zk.processTxn (:690). Nothing is
  logged and no snapshot is taken.
- If the stream ends before NEWLEADER, Learner.shutdown keeps the database: `initialized` stays true and
  DataTree.lastProcessedZxid is ahead of the log, which truncateLog cut back to the TRUNC point.
- On reconnect, registerWithLeader sends getLastLoggedZxid (Learner.java:490 -> QuorumPeer.java:1386), which is the
  in-memory value. The leader's LearnerHandler.syncFollower (LearnerHandler.java:780) answers with an empty DIFF.
- The txns applied only in memory are never logged, so the log has a hole inside one epoch.
- At the next restart, the replay (FileTxnSnapLog.fastForwardFromEdits:326 -> listener -> addCommittedProposal) meets
  the hole and throws at :341.
