## 1. The cluster and where things live

- CloudLab `node0`..`node4` (this cluster: 40 logical = 20 physical cores, 251 GB each). `/bulk` is node0's disk, NFS
  at the same path on every node; `/localtmp` is each node's local scratch. Passwordless ssh between nodes and to GitHub.
- Repos on the cluster: GraphChecker `/bulk/GraphChecker` (worktrees `/bulk/wt/gc-*`), forks `/bulk/hadoop`,
  `/bulk/hbase`, `/bulk/zookeeper`, `/bulk/solr` (worktrees `/bulk/wt/<sys>-bug-*`, `/bulk/wt/hadoop-bug-*`).
- Tree sets (what a run reads): `/bulk/trees/*`; Maven repositories `/bulk/m2/*` (`dot-m2`, `dot-ant`, `dot-ivy2` are the
  nodes' `~/.m2`, `~/.ant`, `~/.ivy2`); snapshots (what a run executes): `/bulk/gc-run/*`; run outputs:
  `/bulk/gc-out/*`; the shared host ledger `/bulk/gc-out/hosts` (cores in hundredths on every branch below).
- VM images: `/bulk/vm/hbase/j2sdk-image` (used by HDFS and HBase), `/bulk/vm/zookeeper/j2sdk-image`,
  `/bulk/vm/solr/j2sdk-image`.
- Analysis and agent notes: `/bulk/analysis/` -- the buggy-detect work is in `/bulk/analysis/buggy-detect-2026-10-26/`
  (BRIEF.md, RESULTS.md, one `<jira>-notes.md` per bug, setup notes, review logs); the first HDFS round in
  `/bulk/analysis/hdfs-buggy-2026-10-25/`.
- Rules you must keep (RULES.md has them in full): general fixes only, no per-case engine code, no fallback or dead code,
  no comments in GraphChecker Java code; a tree workaround makes an order controllable or a value trackable, never
  switches the fatal outcome, and is marked `// GraphChecker:`; CONFIRM and REPRODUCE stay; kill only by explicit pid or
  process group (`tools/rounds/stop-run.sh` for runs -- never name the run's OUT path in your own command line, it
  kills the caller); never `git add -A`; never rebuild a tree or snapshot a run reads; commits authored
  `Zhenyu Li <zhl136@ucsd.edu>` ending `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; push only what the
  owner asks. Engine changes on the buggy-detect branches were each independently reviewed before they counted.

## 6. Running a case (any buggy-detect branch)

The brief `/bulk/analysis/buggy-detect-2026-10-26/BRIEF.md` has the per-system layout and commands. In short: snapshot
with `bash tools/lib/worktree-add.sh /bulk/gc-run/<name> <commit> --detach` then `mvn -q -o package -DskipTests` on a
node; a tree set is a detached worktree of the fork at the case's commit plus its Maven repository; run with
`env GC_OUT=<dir> GC_TREES=<tree set> CAUSYNTH_CUSTOM_JDK_HOME=<vm image> CASES=<case> CASE_TIMEOUT_SECONDS=21600
PRUNE=0 tools/rounds/launch-round.sh <snapshot> <ROUND>`; read with `tools/rounds/round-verify.sh`,
`tools/analysis/vacuity.py`, `tools/analysis/smt-legend.py`, and `experiments/accept/report.py` (each case needs its
`EXPECTED_MECHANISM` row).
