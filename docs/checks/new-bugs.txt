1. HDFS — hdfs-bugs-slowdisk-zero（HDFS.txt #15）
   把"最多排除慢盘数"改成 0 之后，旧的排除列表仍然生效，SSD 写入被持续否决
==========================================================================================

参与的状态
  * 管理端配置 dfs.datanode.max.slowdisks.to.exclude：0 是文档定义的"不排除任何盘"（hdfs-default.xml）。
  * DataNode 的慢盘检测线程：DataNodeDiskMetrics 周期性地计算慢盘，把结果发布到 slowDisksToExclude 列表。
  * DataNode 的卷选择器：FsVolumeList 按 slowDisksToExclude 过滤候选卷，再交给 RoundRobinVolumeChoosingPolicy。
  * NameNode 的块放置：按存储策略（ALL_SSD）把块分给有 SSD 的 DataNode，它不知道 DataNode 本地的否决列表。
  这四处状态分别由管理员 RPC、检测线程、DataNode 写线程和 NameNode 维护，没有任何一处保证"最大值为 0 时列表为空"。

因果链
  1. 最大排除数为 1 时，检测线程把唯一的 SSD 判为慢盘，发布到 slowDisksToExclude。
  2. 管理员调用公开的 DataNode.reconfigureProperty(max.slowdisks.to.exclude, "0") 并成功；
     DataNode.reconfSlowDiskParameters 只更新 DataNodeDiskMetrics.maxSlowDisksToExclude。
  3. 检测线程 DataNodeDiskMetrics.startDiskOutlierDetectionThread 只在 if (maxSlowDisksToExclude > 0) 分支内
     替换 slowDisksToExclude。最大值变成 0 后，以后每一轮都跳过这个分支，旧列表永远留着，没有任何一处清空它。
  4. 客户端写 ALL_SSD 文件，NameNode 正常分配 SSD 块。DataNode 上 FsVolumeList.getNextVolume / chooseVolume
     按旧列表把唯一的 SSD 过滤掉，候选卷为空。
  5. 致命 guard：RoundRobinVolumeChoosingPolicy.chooseVolume 的 if (volumes.size() < 1)，抛
     DiskOutOfSpaceException("No more available volumes")；DataXceiver 写块失败，客户端得到 IOException。
     同一路径的第二次写入会重新分配块，并再次命中同一 guard；同时普通 DISK 写入正常，说明集群其余部分健康。

为什么难以自行恢复
  配置已经是"不排除"，检测线程也在运行，但它永远不会再进入替换列表的分支。原样重试写入、等待检测周期都无效，
  只能重启 DataNode，或做其他改变状态的修复。

复现（bug_study）
  上游 Hadoop b4daa4632196（3.6.0-SNAPSHOT）。一 NN、一 DN、一 SSD + 五 DISK 的 MiniDFSCluster；
  TestDisabledSlowDiskExclusion 为 1/0/0。测试只用已有的 addSlowDiskForTesting 钩子提供一次历史慢盘样本，
  不替换卷选择器、RPC 或重试。

先例（有界检索）
  HDFS-16397 引入慢盘参数的动态重配置，没有报告这个状态转换。HDFS-17936 报告了同一个终端异常，但它的根因是
  排除开启时检测不区分存储类型；本例是关闭排除（设为 0）后旧列表残留，修复位置不同（0 的转换需要清空列表）。

GraphChecker 检查：SAT 已证实
  * 工作负载：自写的 TestCausynthSlowDiskZeroMax#testAllSsdWriteAfterSlowDiskExclusionTurnedOff（现有测试里，
    TestFsVolumeList 发布了慢盘列表但从不改最大值，TestDataNodeReconfiguration 改了最大值但不发布列表、不写文件）。
    流程：把唯一的 SSD 标为慢盘，立刻把最大值改成 0，等几轮检测后写 ALL_SSD 文件。录制的那次运行不失败：
    重配置之后，每一轮检测读到的都是 0。
  * 目标：RoundRobinVolumeChoosingPolicy 的 volumes.size() < 1 分支（我们树的第 84 行）。
  * 找到的世界（STATE_PAIRING_FLIPPED）：把检测线程对 maxSlowDisksToExclude 的一次读取重新配对到重配置之前的值 1
    （INITIAL arm），这一轮便把 SSD 发布进 slowDisksToExclude；卷选择器对 slowDisksToExclude 的读取再配对到这次发布。
    之后各轮读到 0，跳过替换，旧列表留下，过滤后候选卷为空。也就是说，GraphChecker 没有用人为的慢盘样本时序，
    而是在"检测线程与重配置之间的一次读写交错"上找到了同一个致命状态。
  * 证据：round HG9B（system/hdfs aaa2befe7）；polarityDecides 为真；CONFIRM 已证实；cone.py 未绑定变量为 0；
    原生复现（录制版织入，在原生 JDK 上植入 CONFIRM 的顺序行）10/10 在 anchor 触发致命 guard（NP7 与 HG9B 两轮）。
    输出：/bigtemp/vnr3ne/gc-out/hdfs-study/accept-HG9B-11/。

2. ZooKeeper — zk-bugs-quota-init（ZooKeeper.txt #01）
   配额的 limit 节点先于 stats 节点提交，中断后原样重试永远失败，硬配额也不再生效
==========================================================================================

参与的状态
  * 客户端的 SetQuotaCommand.createQuota：先在 /zookeeper/quota/<path>/zookeeper_limits 创建 limit 节点，
    再在另一个独立事务里创建 zookeeper_stats 节点。
  * 服务端 DataTree：limit 节点一提交，就把路径登记进配额 trie。
  * 服务端的配额检查 ZooKeeperServer.checkQuota 与 DataTree.updateQuotaStat：都依赖 stats 节点存在。

因果链
  1. createQuota 提交了 limit 节点；在创建 stats 节点之前，客户端被中断（bug_study 是一次 InterruptedException；
     ConnectionLoss 等故障同样可以中断）。此时 limit 存在、stats 不存在，两个节点不是一个原子操作。
  2. 同一个 createQuota 原样重试：发现 limit 已存在，进入"更新"分支，直接 getData(statPath)，不会补建 stats。
  3. 致命 guard：服务端 DataTree.getData 的 if (n == null) throw NoNodeException。每次重试都命中，修复路径永远到不了。
  4. 更糟的是，配额 trie 已登记该路径，但 checkQuota 和 updateQuotaStat 发现没有 stats 节点就直接返回：
     硬计数上限为 1 的路径下，额外的子节点创建也会成功，配额失效。

为什么难以自行恢复
  原样重试 createQuota 进入的分支要求 stats 已存在，永远补不上它。只有运维人员手工创建或删除配额元数据才能修复。

复现（bug_study）
  上游 ZooKeeper aafd344e，真实五节点 QuorumBase、公开 API；
  QuotaCoordinationRegressionTest.interruptedQuotaInitializationCannotBeRetriedAndDisablesEnforcement，BUILD SUCCESS。

先例（有界检索）
  ZOOKEEPER-1448（启动时 replay/trie 缺陷）和 ZOOKEEPER-2563（部分删除）都已修复，均不是"limit 先于 stats、中断后重试
  永久失败"。

GraphChecker 检查：SAT 已证实
  * 工作负载：树里的 CausynthQuotaRetryTest#raisesARetriedHardQuota（owner 批准）：客户端设硬配额，遇 ConnectionLoss 时重试，
    然后提高配额，由服务端执行配额。
  * 目标：服务端 getData 在 NoNode guard 处的第 6 次出现（REGION.860d3eb6…#6），即走"更新"分支那次调用对 stats 的读取。
  * 找到的世界（MARKER_FLIPPED）：在 limit 节点的 create 上翻转 ZooKeeper WRITE 门的 FAULT 根，即写已提交、客户端却收到
    ConnectionLoss。于是没有 stats，客户端重试发现 limit 已存在，走更新分支读 stats，命中服务端 NoNode guard。
    这与 bug_study 的中断点（limit 之后、stats 之前）是同一个状态窗口，故障形式不同。
  * 证据：main 分支 round V25（自 V12 起持续 PASS）；polarityDecides 为真；CONFIRM 已证实；cone.py 通过；
    原生复现 10/10（植入 10 次、10 次触发致命 guard、10 次在 anchor）。输出：/bigtemp/vnr3ne/gc-out/accept-V25-zk-bugs-quota-init/。

3. ZooKeeper — zk-bugs-election-offer（ZooKeeper.txt #05）
   选主 recipe 列出竞争者后、读取其 offer 前，竞争者的 offer 消失；失败的 start() 留下自己的孤儿 offer，堵死选主
==========================================================================================

参与的状态
  * 选主 recipe LeaderElectionSupport：内存字段 leaderOffer 只记住自己最新的 offer 路径。
  * ZooKeeper 上的 ephemeral sequential offer 节点：每个候选者一个，按序号决定谁是 leader。
  * 列表与读取是两次独立的 RPC：getChildren 列出所有 offer，然后对每个 offer 单独 getData。

因果链
  1. 工作者调用 start()：makeOffer 提交自己的 offer n_1，并记到 leaderOffer。
  2. determineElectionStatus 列出子节点，其中包括竞争者的 n_0；toLeaderOffers 对每个子节点分别 getData。
  3. 在列出之后、读取之前，竞争者正常 stop()，删除了 n_0。
  4. 致命 guard：服务端 DataTree.getData 的 if (n == null) throw NoNodeException。start() 捕获异常后只发出 FAILED 事件，
     不删除自己已提交的 offer n_1。
  5. 后果：n_1 是孤儿但仍是最早的子节点。另一个独立会话的新候选者永远停在 READY，不能当选；同一工作者重试 start()
     会再建 n_2，并覆盖 leaderOffer，于是 n_2 排在孤儿 n_1 之后，同样不能当选；stop() 只删记住的 n_2，孤儿留下。
     在工作者会话过期之前，服务没有 leader。

为什么难以自行恢复
  失败的第一次调用已经堵死服务，而且发生在任何重试之前；原样重试只会多一个排在孤儿后面的 offer。
  只能等会话过期，或手工删除孤儿节点。

复现（bug_study）
  上游 ZooKeeper aafd344e，真实五节点 QuorumBase；LeaderOfferReadRaceRegressionTest 为 1/0/0。
  测试只在真实 getData RPC 之前暂停，通过另一个公开客户端删除竞争者，没有 mock 任何服务端方法。

先例（有界检索）
  ZOOKEEPER-1225 是"start() 成功后再次调用导致第二个 offer"；本例是第一次 start() 因竞争者正常删除而失败、留下孤儿，
  而且在任何重复调用之前就堵死了服务。1225 提出的"拒绝重复 start()"修不了这里。ZOOKEEPER-1209 是断连客户端仍报 ELECTED。

GraphChecker 检查：SAT 已证实
  * 工作负载：recipe 自带的 LeaderElectionSupportTest#testNodes3（三个候选者，每个都列出 offer 并按顺序读取）。
  * 目标：服务端对某个 offer 的第二次 getData（REGION.860d3eb6…#2）。前两次读的都是 n_0：先是创建者自己，然后是一个竞争者，
    而后者的读取可能与创建者的 stop() 竞争。
  * 找到的世界（STATE_PAIRING_FLIPPED）：把服务端对该 offer 的查找重新配对到创建者 stop() 的删除之后，命中 NoNode guard。
    这是 bug 的触发点；孤儿 offer 堵死选主等后续后果，不在本检查的致命 guard 之内。
  * 证据：main 分支 round V25（自 V18 起持续 PASS）；polarityDecides 为真；CONFIRM 已证实；cone.py 通过。
    原生复现：V25 时 main 的原生植入还不支持只有重配对（不移动根）的世界（NATIVE_PLANT_UNSUPPORTED），所以没做；
    system/hdfs 上的原生植入后来已能植入 CONFIRM 的顺序行，ZooKeeper 轮次时重跑即可补上。
    输出：/bigtemp/vnr3ne/gc-out/accept-V25-zk-bugs-election-offer/。

4. ZooKeeper — zk-bugs-container-reuse（ZooKeeper.txt #33）
   容器节点清理器按路径删除，删掉了同一路径上新建的下一代节点
==========================================================================================

参与的状态
  * ContainerManager 的周期清理：getCandidates 先快照"空的容器节点"的路径集合，checkContainers 再逐个发送只含路径的
    DeleteContainerRequest(P)，中间还会 sleep。
  * 服务端预处理 PrepRequestProcessor.deleteContainer：只检查当前 P 的子节点数为 0、类型是容器；不检查 czxid、cversion
    等"代"信息。
  * 客户端：可以删除旧的 P，并在同一路径上建新节点。

因果链
  1. 旧容器 P 曾有子节点，子节点删光后为空（cversion > 0），被放进本轮候选。
  2. 发送删除请求之前，客户端删掉旧 P，在同一路径上新建一个节点（bug_study 演示了新的空容器，以及新的 PERSISTENT 节点）。
     新节点刚出生，本该受 maxNeverUsedIntervalMs 保护；重新扫描时它也确实不在候选里。
  3. 清理器发出旧的 DeleteContainerRequest(P)。服务端只看到"当前 P 为空"（对 PERSISTENT 节点也成立），就把新一代删了。
  4. 致命 guard：客户端随后 getData(P)，命中服务端 FinalRequestProcessor 的 NoNode。数据丢失，并且稳定复现。

为什么难以自行恢复
  被删的是用户新写入的节点，数据已经没了。请求里没有任何代信息，服务端无法分辨"旧代"和"新代"。

复现（bug_study）
  上游 ZooKeeper，五节点 quorum；ContainerReplacementCoordinationRegressionTest 的两个测试为 2/0/0。
  测试只在 ContainerManager.postDeleteRequest 提交前暂停已选中的真实清理请求。

我们的树（gc/zk-unified，branch-3.9）中的核对
  ContainerManager.getCandidates :159-190，checkContainers :126-145，PrepRequestProcessor.deleteContainer :332-346
  只检查 childCount > 0 与 EphemeralType NORMAL；新建的 PERSISTENT 节点 owner 为 0（VOID），同样会被删除；
  客户端 getData 在 FinalRequestProcessor:709 得到 NoNode。

GraphChecker 检查：已接纳，尚未建 case
  * 预期机制：客户端对 P 的读取与清理器删除之间的 STATE 重配对（与 election-offer 同类）。
  * 需要：一个自写的 ClientBase 测试作为工作负载（没有现成测试同时覆盖清理和同路径重建）。ZooKeeper 轮次再做。

5. Solr — solr-bugs-reindex-cleanup（Solr.txt #04）
   并发别名阻断 REINDEX 中止清理，源集合永久只读
==========================================================================================

参与的状态
  * 异步 REINDEXCOLLECTION(S -> T)：先建目标 T 和 checkpoint 集合，再把源 S 标成只读；中止时 cleanup 应删除 T，
    并清除 S 的只读属性和 reindex 状态。
  * CREATEALIAS(A -> T)：只锁别名 A，不锁目标 T，可以在 reindex 建好 T 之后、清理之前成功。
  * DeleteCollectionCmd.checkAliasReference：被别名引用的集合不许删除。

因果链
  1. REINDEXCOLLECTION 建出 T，并把 S 标成只读（REINDEXCOLLECTION 的锁级别是 NONE）。
  2. 并发的 CREATEALIAS(A, T) 成功发布 A -> T。
  3. 管理员发出 REINDEXCOLLECTION(cmd=abort)。cleanup 删除 T 时，checkAliasReference 发现 A 引用 T，抛
     SolrException(BAD_REQUEST, "Collection : T is part of aliases")。
  4. 这个异常从 cleanup 直接抛出，后面"清除 S 只读、删除 S 的 reindex 状态"的步骤都没执行。任务状态为 FAILED，S 仍只读。
  5. 致命 guard：之后对 S 的公开 add 在 DistributedZkUpdateProcessor.processAdd 的 if (isReadOnly()) 处抛
     SolrException(FORBIDDEN, "Collection S is read-only.")（HTTP 403）；原样重试相同 add 一样失败。

为什么难以自行恢复
  目标删除被别名保护本身是合理的；缺陷在于目标删除失败中断了对源集合的状态恢复，属于跨对象清理的部分提交。
  没有任何后台过程会把 S 改回可写，需要管理员手工解除只读，并处理残留的 T 和 A。

复现（bug_study）
  上游 Solr 91cbb6a3（11.0.0-SNAPSHOT）。两节点 MiniSolrCloudCluster；TestReindexAbortAliasCleanupRace 为 BUILD SUCCESSFUL，
  只用了 Solr 原有的 reindexLatch 固定时序，不注入异常。

先例（有界检索）
  SOLR-11127 是 REINDEXCOLLECTION 的功能设计，SOLR-18083 是只读集合的一般行为修复，都没有"目标别名阻断中止清理"的先例。

GraphChecker 检查：已建 case，尚无 witness
  * 分支 solr-bug-reindex（Solr 8.11 的 gc/solr-bugs 树）。预期 witness 是 cleanup 之前 CREATEALIAS 之后 setData 写门上的故障

   leader 的 publish(ACTIVE) 因 ZooKeeper ConnectionLoss 失败后注销自身选举，state.json 却仍记它为 ACTIVE leader，
   此后发往该 shard 的每个更新都被拒绝（503），直到节点重启
==========================================================================================

参与的状态
  * 本地：CloudDescriptor.isLeader（JVM 内存），ElectionContext（ZkController.electionContexts）。
  * ZooKeeper：/collections/<c>/state.json 中该 replica 的 leader=true 与 state；/collections/<c>/leaders/<shard>/leader
    选举注册节点；/overseer/queue 上的状态消息。

因果链（Solr 8.11.4 = 我们的树 gc/solr-final*；行号为该树）
  1. core 创建时 ZkContainer.registerInZk -> ZkController.register：赢得选举，ShardLeaderElectionContext.runLeaderProcess
     写 leader 注册节点、经 Overseer 把 state.json 中本 replica 标为 leader，并 setLeader(true)（:264）。
  2. register 末尾 publish(desc, ACTIVE)（ZkController:1362 -> publish:1691 -> ZkDistributedQueue.offer:328 ->
     SolrZkClient.create）。ZkCmdExecutor 只重试 ConnectionLoss；若整个重试窗口内连接一直断续（每次尝试都 ConnectionLoss，
     而会话未过期），create 最终抛 ConnectionLoss（某次尝试可能已写入，Overseer 照样把它标为 ACTIVE）。
  3. register 的 catch（:1370-1371）调用 unregister -> context.cancelElection（:1763）->
     ShardLeaderElectionContext.cancelElection:78 setLeader(false)，并删除自己的 leader 注册节点。ZkContainer.registerInZk
     对 KeeperException 只记日志（不 publish DOWN）。state.json 没有任何写者撤销本 replica 的 leader 标记。
  4. 致命 guard：之后的 add 到达该 core，DistributedZkUpdateProcessor.setupRequest:647 由 getLeaderRetry（state.json）判定
     isLeader=true，doDefensiveChecks:990 读 cloudDesc.isLeader()=false，重读 5 次（每次 500 ms）后在 :1031 抛
     SERVICE_UNAVAILABLE "ClusterState says we are the leader (...), but locally we don't think so"。

为什么难以自行恢复
  core 已退出选举；同 shard 若无其他可当选的副本（PULL 副本不参选；只有一个 NRT/TLOG 时即如此），没有人重新选举，
  state.json 一直指向它。会话未过期，所以 OnReconnect 的 markAllAsNotLeader/重新注册不会发生。客户端重试无用
  （SOLR-11685 在 9.4 让 SolrJ 把此错误当作暂时性错误重试，但这里不是暂时的）。只有重启节点或手工 FORCELEADER/重载能修复。

触发条件的现实性
  register 的 catch 对任何逃出 publish(ACTIVE) 的 KeeperException 都走同一条链。现实的触发是 ConnectionLoss 穿过
  ZkCmdExecutor 的全部重试（zkClientTimeout=30 s 时 8 次尝试、约 42 s 的退避）而会话始终存活：持续断开 42 s 会让 30 s
  会话过期（之后走 SessionExpired 的重新注册路径而自愈），所以需要连接"断续"而非"全断"（网络抖动、ZK 服务器 GC 停顿）。
  与 09/40 的 lost-watch 候选同一类触发（终端 ConnectionLoss、会话存活）。SGF2 的 witness 用的是 OperationTimeoutException
  （ZkCmdExecutor 不重试它，一次即逃出），但 ZooKeeper 的 Java 客户端与服务端从不产生 OPERATIONTIMEOUT（3.6.2 即 Solr 8.11 所用版本的 jar 与 3.9 源码中只有
  KeeperException 的定义），所以现实性仍以 SC5 证实的 ConnectionLoss 世界为准；两者在 register 之后的链相同。
  OperationTimeout 自 solr-ztimeout 起不再是故障种类：在 gc/solr-final9 上 38 的 witness 应为 create 边界门上的 ConnectionLoss。

上游 main 中仍在

  ShardLeaderElectionContext.cancelElection:89-93 setLeader(false)；DistributedZkUpdateProcessor:1155-1158 同一 guard。

附：GraphChecker 对新 bug 的检查方法（简述）
==========================================================================================
  * 每个 bug 在系统树里用 @CausynthExceptionTarget("<case id>") 标出致命 guard 的那个 throw；工作负载尽量用系统自带的
    cluster 测试，没有现成测试时才自写（例如 slowdisk-zero）。
  * GraphChecker 从一次不失败的录制出发，系统地翻转切片上的符号分支和决定它们的根：门上的故障、时钟、配置，以及消息和
    共享状态读的配对。每个翻转后的世界都在 concolic JVM 上重放，被接纳的重放最终融合成一个 candidate.smt2，由 z3 判定。
  * SAT 必须经 CONFIRM 在真实程序里重放证实；再做原生复现：用录制版织入在原生 JDK 上植入 CONFIRM 的世界，跑 10 次，
    统计在 anchor 处触发致命 guard 的次数。
  * 检查与验收的完整规则和踩过的坑：GraphChecker 仓库 docs/handover/CHECKING.md；每个 check 的实时状态：docs/checks/README.md。
