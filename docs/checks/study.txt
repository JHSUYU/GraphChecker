GRAPHChecker study: heuristic discovery of ad hoc coordination checks
=====================================================================

Snapshot and meaning of the numbers
-----------------------------------
This note records the existing independent classifier under
tools/coordination_classifier in the local GraphChecker workspace, its
exact-version inputs, and every one of its 144 final YES sites. It is a
research inventory, not a claim that any listed check is buggy.

The broad input inventory contains 26,536 explicit Java failure sites:
throw, Java assert, direct check calls, and process-exit sites. The
recorded broad scan retained 1,251 candidate sites. The second Soot
fact pass inspected 8,382 sites (broad YES sites plus selected checks
with guard/read evidence), resolving all 8,382 target methods in this
local artifact set. The final binary rule labels 144 YES:

                   all checks  broad YES  final YES  named workload  guard confirmed
  HDFS 3.4.3           10,718        532         53              51               50
  HBase 2.6.6           6,657        225         38              23               23
  Solr 8.11.4           8,034        375         40              26               26
  ZooKeeper 3.8.7       1,127        119         13              11               11
  TOTAL                26,536      1,251        144             111              110

There are 111 sites with a named existing cluster-based JUnit workload.
For 110 of them, manual reading gives a production path that evaluates
the relevant guard, regardless of whether it takes the failure branch.
HDFS-18 has a named workload but its guard requires a second provided-
storage update not guaranteed by that test; it is marked
WORKLOAD_UNCERTAIN rather than TESTED. The 33 sites with no identified
workload comprise 24 NO_PATH and 9 UNCERTAIN. Thus the strict source
audit has 110 confirmed, 24 with no path found, and 10 unresolved.
These are source-derived judgments, not observed JaCoCo/JVM condition
hits. A test that only mocks a component, or enters a method but
returns before the guard, does not establish guard coverage.
For this audit a cluster test starts MiniDFSCluster or MiniJournalCluster
(HDFS), MiniHBaseCluster/LocalHBaseCluster (HBase), a SolrCloud cluster
including its ZooKeeper/Jetty nodes (Solr), or live ZooKeeper quorum
peers (ZooKeeper). A check evaluated during @BeforeClass/@BeforeAll
cluster startup counts for the named test that uses that setup.
Solr's TestPullReplica.testAddDocs is a valid JUnit3-style test method:
LuceneTestCase selects RandomizedRunner with LuceneJUnit3MethodProvider,
which discovers public non-static no-argument test* methods even without
an @Test annotation. Its @BeforeClass starts a two-node SolrCloud cluster.

Implemented static-analysis algorithm
-------------------------------------
1. Candidate inventory. The cached out/<system>.decisions.jsonl files
   record site ID, bytecode/Jimple unit index, source line, site kind,
   exception, candidate guards, and conservative evidence gathered by
   the earlier CoordinationScanMain pass. The broad scanner is present
   in the existing GraphChecker assembly JAR, but its Java source is
   absent from the current checkout. Thus this note describes the
   second-stage implementation precisely and does not invent details
   of the earlier scanner. --rescan calls that prebuilt scanner.

2. Site-local Soot facts. InteractionFacts.java configures Soot with
   the listed JARs, permits phantom references for missing optional
   dependencies, constructs a BriefUnitGraph and SimpleLocalDefs for
   each concrete target method, and re-resolves the actual IfStmt
   operands controlling the failure. An IfStmt is a failure gate when
   exactly one CFG successor reaches the target without revisiting the
   branch. Direct checkState/checkArgument/assertTrue/assertFalse calls
   use their first argument as the predicate; the pass also recovers
   javac-materialized boolean constants from their selecting branches.
   Each condition is traced backward through local definitions,
   arithmetic/casts, fields, parameters, calls and up to three levels
   of short getter/return summaries (callee <=160 Jimple units;
   recursion/visit limits 18/128). The pass records left/right operand
   provenance, collection lookups, and the nearest failure-gate
   distance. It searches concrete field stores and common Map/Set/
   atomic-container mutations, including an enclosing class for a
   nested class. It records candidate writer conditions and whether
   declared event-root methods directly call a writer. A writer is
   considered branch-controlled when a condition-bearing branch's two
   successors have different reachability to that write. These are
   bounded, conservative facts, not a complete alias or dependence
   analysis.

3. One binary YES/NO decision, with no ranking or top-k quota.
   Unresolved targets and configured expected request errors are NO.
   A considered guard must be resolved, be a failure gate, be at most
   40 CFG edges from the target, and be no more than 15 edges farther
   than the closest gate. Constructor and class-initializer stores do
   not establish later mutable state. Assertion-enabling fields and
   value-object fields are filtered. The remaining direct writers
   establish retained mutable views. A relational predicate can use
   two fields, a field and a parameter, a two-sided comparison, or a
   collection lookup. The decision returns YES on any of these actual
   implementation witnesses:

   propagated-view: a retained view is updated by a carried value,
     branch-dependent state read, or verified event callback, and the
     failure guard relates that view to another input/view.
   event-root-view: an event-root callback updates retained state from
     a parameter and a control-component guard relates the result.
     This captures primitive event values without requiring a DTO.
   independent-views: a control-component guard compares two separately
     writable histories, with branch dependence; local numeric
     capacity comparisons need additional interaction evidence.
   state-read-and-update: a guard reads state through a configured API
     while a retained field also has a branch-controlled writer.
   message-state-check: a received message/version/epoch value is
     compared with mutable state written in a separate event; a
     deliberately thrown transition signal is excluded.
   remote-state-check: an interaction API supplies the state used in
     the guard, even if the producer's internal field writer is opaque;
     carrier types and state-getter/predicate signatures provide the
     connection.
   cached-refresh: an exhausted remote refresh is checked against a
     mutable cached view (used by the Solr adapter).

   If no witness matches, the answer is NO = insufficient interaction
   evidence. YES is a candidate ad hoc coordination check, not a
   reachability proof; NO is not proof of absence. Several independent
   states can participate, and the rule does not require all
   authoritative states to reside in a control-plane process. A
   control-plane participant is represented by configured component
   roles or state APIs, but a data-plane check can qualify through
   propagated/interacting state. The shared-state, RPC, watch, HTTP,
   and durable-read links here are approximated by field writes,
   carrier types, event roots and API signatures. This standalone
   classifier does NOT pair individual RPC sends/receives, build a
   dynamic causal graph, or implement GraphChecker's iterative
   exploration closure.

4. Validation and iteration. Five source-audited revisions changed
   the final totals 191 -> 149 -> 170 -> 140 -> 144; the final rule
   excludes simple type/enum checks, parser/configuration checks,
   generic request payloads, allocator/capacity checks, and distant
   unrelated cluster-state conditions unless the actual failure
   predicate has an interaction witness. validate_results.py checks
   24 manually audited positive/negative controls and all four counts.

Per-system adaptations used to run this analysis
------------------------------------------------
All systems use the SAME decision code. boundary_adapters.json contains
regex descriptions of component roles, communication/state APIs, event
callers/roots, carrier types, and excluded value types. It contains no
per-site YES whitelist. artifact_manifest.json fixes the local JAR
inputs. Its source revision and SHA-256 values are provenance
metadata; run_analysis.py checks path existence but does not recompute
those hashes or verify the source revision.

HDFS 3.4.3:
  Production: hadoop-hdfs and hadoop-hdfs-client 3.4.3 JARs.
  Auxiliary classpath: hadoop-common 3.4.3.
  Control-side roles: NameNode, block management, QJournal.
  Event hints: DataStreamer.ResponseProcessor, BPServiceActor
  heartbeat/offer loop, Balancer KeyManager's BlockKeyUpdater.
  Carriers/read APIs: ExportedBlockKeys, DataEncryptionKey,
  NNHAStatusHeartbeat, NamespaceInfo, DataNode commands,
  LocatedBlock, HDFS protocol APIs, FSImage/EditLog and journal reads.
  Exclusions: tools and fsck-only components, plus simple HDFS
  value-object types. These hints keep heartbeats, key refresh,
  recovery, namespace and journal history visible without calling
  every wire value a coordination dependency.

HBase 2.6.6:
  Production: hbase-server, hbase-client, hbase-common,
  hbase-zookeeper and hbase-procedure 2.6.6 JARs.

Solr 8.11.4:
  Production: solr-core and solr-solrj 8.11.4 JARs.
  Auxiliary classpath: lucene-core 8.11.4 and ZooKeeper 3.8.7.
  Control-side roles: cloud/common.cloud, core and handlers.
  Event hints: ZkStateReader process/refresh and
  IndexDeletionPolicyWrapper.onCommit. Carriers: Aliases,
  ClusterState, DocCollection and ZkNodeProps. State APIs:
  SolrZkClient, ZkStateReader, replication file-list/index reads and
  HttpSolrClient requests. The adapter recognizes getAliases and
  fetchLiveNodes as remote cache refreshes. It excludes simulation/
  designer components and conservatively rejects BAD_REQUEST checks
  as expected request errors; this may lose some true coordination
  cases.

ZooKeeper 3.8.7:
  Production: zookeeper and zookeeper-jute 3.8.7 JARs.
  No extra auxiliary JAR is listed in the manifest.
  Control-side roles: quorum/persistence, ZKDatabase/DataTree and
  ZooKeeperServer. Event hints: Follower/Leader packet processing,
  SessionTrackerImpl.run, Leader.lead and LearnerSessionTracker
  session commit/removal roots. Carriers: QuorumPacket, StateSummary
  and ReplyHeader. State APIs: packet reads, transaction-log/snapshot
  reads, committed-log and epoch-file reads. The primitive-valued
  event-root treatment is needed for session and epoch checks.
  Configuration-only QuorumPeerConfig and the intentional
  processReconfig transition signal are excluded.

Reproducing the local classification (not included on this study branch):
  python3 tools/coordination_classifier/run_analysis.py
  python3 tools/coordination_classifier/validate_results.py

Use JDK 8 and the existing GraphChecker assembly JAR. The default run
reuses ignored out/*.decisions.jsonl files, compiles InteractionFacts,
extracts Soot facts, then classifies. --rescan asks the prebuilt
assembly JAR's CoordinationScanMain to regenerate the broad scan;
--reuse-facts only reruns the final Python decision. This study branch
intentionally contains only this TXT, not the local independent tool,
ignored outputs, release source trees or Maven cache. A clean checkout
of this branch alone therefore cannot regenerate the numbers.

Catalog format
--------------
Each item below is one final YES-classified candidate, ordered exactly
as its system's classified.jsonl YES rows. The location is the
release-relative Java source path and the recorded SOURCE LINE OF THE
FAILURE SITE, followed by the complete Soot method signature and
#uN unit ID; a guarding IfStmt can have a different line. The
siteKind/exception and YES rule are included. TESTED marks one of the
110 sites with a confirmed cluster JUnit path; its test name is
spelled out on that item. WORKLOAD_UNCERTAIN identifies HDFS-18, the
one additional named workload whose guard is not source-confirmed.
NO_PATH and UNCERTAIN are audit judgments, not different static-
classifier labels. The short audit note explains why the named test
reaches the guard or why coverage was not established.
